## Referencing preflight data from inflight code - Analogy

In the previous step, we've seen inflight code that naturally referenced a bucket that was defined in the preflight phase (the code is also in the editor of this step).

This interaction feels natural because it's similar to code for single machines. One that instantiates an Operating System services in one scope (think local file system instead of a cloud bucket) and then uses it from a different scope (that of a function).

Such code is very common, and can look something like this in JavaScript and Node.js:

```javascript
const fs = require('fs');
const path = require('path');

// Create a folder to store the files
let dirPath = path.join(__dirname, '/myFolder')
fs.mkdirSync();

function helloWorld(payload){
    // add file to the folder
    fs.writeFile(path.join(dirPath, 'hello.txt'), `Hello, World! with this payload: ${payload}}`);
}
```

The main difference between such code for a single machine and our Wing code for the cloud (in the Editor) is that our Wing code is split into two execution phases: 
1. Preflight code that sets up the services at compile time (function and bucket).
2. Inflight code to uses the bucket at runtime - ***from different machines, amd possibly much later***. 
   
Another difference is that the Wing services we use are not Operating System Services (like a file system), but cloud services (like a bucket and a function).

Making our cloud code behave like code for single machines saves us the need to write a lot of the glue-logic and boilerplate code that is needed when developing cloud applications with traditional tools.
